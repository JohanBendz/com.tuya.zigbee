# Maintaining Tuya Zigbee for Homey

This repository has accumulated support for a large number of Tuya Zigbee variants over several years. The main maintenance principle is therefore **preserve installed-device behaviour unless a change has a clear reason and can be tested**.

## Sources of truth

- `.homeycompose/app.json` and the other Compose files are the source for the Homey manifest.
- Root `app.json` is generated by Homey Compose and must not be edited manually.
- `drivers/*/driver.compose.json` is the authoritative source for Zigbee pairing identities.
- `SUPPORTED_DEVICES.md` is a human-readable compatibility reference.
- `lib/TuyaDataPoints.js` contains shared Tuya datapoint definitions used by several drivers.

## Device identity

A retail product name is not a reliable compatibility key for Tuya hardware.

When evaluating or adding a device, capture:

- `manufacturerName`
- `modelId` / `productId`
- endpoint IDs
- input/output clusters
- relevant Tuya datapoints for TS0601/custom-cluster devices

Use a full Homey Zigbee interview whenever possible.

## Adding device support

Prefer the smallest safe change.

1. Check whether an existing driver already represents the device behaviour.
2. Compare the Zigbee interview with the driver's existing endpoint/cluster contract.
3. Add the manufacturer/product identity to the existing driver when behaviour is genuinely equivalent.
4. Add new protocol handling only when the device differs functionally.
5. Avoid changing capability order or removing capabilities from existing drivers without an explicit migration plan.
6. Document the new identity in `SUPPORTED_DEVICES.md`.

## Shared code

Changes under `lib/` can affect many drivers at once. Treat changes to shared clusters, datapoint parsing and shared light behaviour as higher risk than adding an identity to one driver.

Do not enable global Zigbee debug logging or datapoint sniffing in release code. Temporary diagnostics should be clearly scoped and removed before release.

## Dependencies

`homey-zigbeedriver` and `zigbee-clusters` are coupled through peer dependency compatibility.

Dependency upgrades should be handled as dedicated work, validated separately from device additions, and tested against representative device families. Do not combine broad dependency upgrades with unrelated maintenance changes.

## Validation

Before merging or releasing:

```bash
npm ci
npm test
npm run validate
```

GitHub Actions deliberately generates `app.json` with Homey Compose **before** any repository test or manifest/index check consumes it. This prevents stale or hand-edited root manifests from becoming an accidental source of truth.

CI order is:

1. install dependencies
2. run Homey Compose build to generate `app.json`
3. verify the generated `app.json` is committed
4. verify `SUPPORTED_DEVICES.md` matches the generated manifest
5. run repository tests against that generated manifest
6. run Homey publish validation
7. verify publish validation did not change `app.json`
8. run the whitespace check

Homey's publish validation checks the generated manifest and publish assets. Static repository tests are intentionally conservative; they do not claim to replace real-device testing.

## Releases

- Keep `package.json`, `.homeycompose/app.json` and generated `app.json` on the same version.
- Add the new version to `.homeychangelog.json`.
- Keep Homey release notes short and user-facing.
- Keep project/developer detail in GitHub documentation rather than the Homey App Store changelog.
- Keep README.md, README.txt, any translated README and Homey changelog entries channel-neutral: no Test/Live/beta labels, candidate status, branch names, rollout dates, CI results or release plans. Store those in MAINTAINING.md, docs/ and GitHub release issues/PRs. Keep support claims accurate; describe added pairing profiles without claiming hardware validation that has not happened.
- Follow Athom's README.txt guidelines: one or two short plain-text paragraphs, no headings, Markdown, URLs, changelog or contributor list. Use manifest source/support fields for links.
- Describe user-visible changes since the previous Live version in the current changelog entry; a documentation-only re-submission still needs the cumulative functional release summary.
- Exclude docs/ and other maintainer-only files from the shipped app using .homeyignore.
- For a changed submission already published under another version, use a new monotonically higher version and keep package-lock.json (including its root package), package.json and Compose metadata aligned.
- Regenerate/validate `app.json` through Homey Compose/CLI; do not hand-edit it.

## Modernization rule

A modernization change should answer one of these questions clearly:

- Does it fix a verified defect?
- Does it make the repository safer or easier to maintain without changing device behaviour?
- Does it add validation that can catch regressions?
- Does it improve documentation of existing behaviour?

If not, it probably belongs in a separate feature/refactor effort.

## Known maintenance items

### Energy meter reset

The historical `resetEnergyMeter` Flow definition is retained for compatibility, but it must not be wired to the old 2-gang implementation. That implementation sent Basic Cluster command `0x00`, which is a factory-reset command in Zigbee rather than an energy-meter reset.

Before enabling energy reset for a driver, verify the actual manufacturer-specific reset mechanism on hardware or from a reliable protocol source. Do not infer a reset command from another Tuya device family.

### TS110E routing

`_TZ3210_ngqk6jia` / `TS110E` remains a documented pairing exception while the dedicated TS110E handling proposed in PR #1350 is reviewed. Do not resolve it by merging the PR blindly; its custom Level Control implementation should first be reconciled with the shared cluster architecture in this repository.
