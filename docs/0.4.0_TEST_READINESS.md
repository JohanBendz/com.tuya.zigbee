# 0.4.0 Test readiness · updated 2026-10-04

**Provisional target:** submit 0.4.0 to the Homey Test channel **6–7 October 2026 only if 0.3.2 has first actually become Live**; otherwise move the Test submission, not the gate. Subject to the *pre-Test static/release gates* below. **The Homey Test channel is our real-world physical testing and community feedback phase: completed physical acceptance of new devices is NOT a prerequisite to publishing Test.** This is a planning target, not a scheduled auto-release. Live/Test versions and Draft PR #1470 are not modified by this document.

## Evidence and scope

- Maintainer-reported 0.3.1 Test adoption on October 2: **over 2,600 installs and no crash or error reports received**. This is a report-status snapshot, not proof that crashes can never occur or that new 0.4 runtime is verified. The 0.3.1 Test line is at commit 7583b4bb2fa91600c2301eb142335312a6a7cac4.
- Preflight compared both generated Homey manifests property for property: 0.3.1 contains **135 drivers**; 0.4 adds **nineteen isolated new profiles**, and all **135 existing driver manifest objects are identical**. No existing Flow-card object or custom capability definition differs. This comparison was turned into a permanent automated baseline test: test/0.4-legacy-manifest-contract.test.js and immutable test/fixtures/0.3.1-manifest-contract.json.
- Nineteen new Compose drivers match 33 distinct Zigbee manufacturerName + modelId pairs pending independent physical acceptance, recorded in docs/0.4.0_PHYSICAL_ACCEPTANCE.md. No existing driver capability migrations or new Flow contracts have been introduced.
- Existing runtime changes requiring extra attention despite identical manifests: four opted-in plug runtimes (smartplug, smartplug_2_socket parent EP1, wall_socket, smartPlug_DinRail) using Tuya relayStatus 0x8002 (#1503); PLUS wall_thermostat's diagnostic-only limiter for high-frequency unmapped DP36 messages (#1501). The thermostat's recognized datapoint values/command handling is not intentionally changed.
- Existing intentional color-temperature audit TODOs (#1502) remain TODOs. The 0.3.1 byte-identical source baseline now includes five core shared Zigbee/Tuya runtime files AND all 15 existing light device.js files; CI checks actual Git blob identities using test/0.4-protected-runtime-contract.test.js. The shared light/runtime stack is too sensitive for a broad, unverified rewrite during this Test preparation window.

## Test-candidate gates

**Gate 1 – build/compatibility:** clean Homey Compose generation; generated app.json and SUPPORTED_DEVICES.md committed and reproducible; full Node test suite including the immutable 0.3.1 contract; Homey app validate at publish level; whitespace; review actual diff from frozen 0.3.1. Any intentional change to an existing driver, custom capability or Flow card must have an explicitly reviewed, issue-linked pinned entry in test/fixtures/0.4-approved-manifest-deltas.json. The 20 protected source files likewise must remain identical to frozen 0.3.1 or require an approved issue-linked exact blob in test/fixtures/0.4-approved-runtime-deltas.json. NEVER modify the 0.3.1 snapshot to make a new change pass. This catches a changed existing driver declaration even if the new code appears harmless.

**Gate 2 – confirmed release order:** **0.3.2 Live BEFORE 0.4.0 Test**, the documentation-only 0.3.2 candidate replaces the original 0.3.1 Live submission plan at the maintainer's request on 2026-10-04. Review the [frozen 0.3.1 runtime feedback](0.3.1_LIVE_REVIEW.md) and [0.3.2 publication correction](0.3.2_PUBLICATION.md), validate the corrected 0.3.2 SHA, complete its separate Athom certification/Live publication, and confirm actual 0.3.2 Live availability before submitting 0.4.0 to Test. **0.3.2 is now in Test and submitted to Athom for Live review; Live approval/publication remains pending (maintainer report 2026-10-04).** Keep the historical 0.3.1 runtime/manifest fixtures at 7583b4bb2fa91600c2301eb142335312a6a7cac4 unchanged. Do not silently merge Draft PR #1470, publish an app, or assume Athom's review timing. Homey Test users may receive newer Test updates: treat moving from 0.3.2 to 0.4 as a meaningful rollout, not a private smoke-test.

**Gate 3 – prepare the physical Test programme, not perform it before publishing:** make the public GitHub issue/reporting path, 33-row exact-identity acceptance matrix, version-safe recovery procedure and reporter instructions ready. No physical pairing, relay/sensor checks or completed hardware acceptance is required to submit 0.4.0 to Test. Once 0.4.0 is available in Test, collect real Homey feedback, prioritizing multichannel EP2/EP3 operation and physical status/Flow (#795/#1500), existing plug power-on-setting regression (#1503), wall-thermostat known datapoints and DP36 log behavior (#1501), and the four added temperature/humidity sensors, MOWE standard-IAS rain sensor (#1288), and three pending standard-IAS flood-sensor fingerprints (#1041; provisional unknown battery cells), and two exact contact + lux profiles (#1298; distinct EF00 endpoint requirements and unknown battery cells), and three plain standard-IAS contact profiles (#1013; Poll Control optional and two unknown battery cell specifications), and two standard IAS PIR + illuminance profiles (#1481; actual lux scaling/battery cells pending). Each manufacturer's actual result is recorded separately; missing or failed Test feedback remains an OPEN issue and feeds subsequent Test patches. Passing a mocked test is never described as physical acceptance.

**Gate 4 – release artifacts:** Follow the [candidate-specific sign-off, Test transition and version-safe recovery plan](0.4.0_RELEASE_PREFLIGHT.md). Keep README and changelog channel-neutral and user-facing; describe added pairing profiles without asserting physical validation. Keep Test/Live status, CI, rollout plans and per-device acceptance in maintainer documentation and GitHub issues. Check the exact supported-device index, pairing instructions/artwork, publish validation at FINAL SHA and documented recovery path. Check source file diff to ensure shared light and global Zigbee cluster handling were not modified inadvertently.

**Separate Live gate (AFTER Test):** evaluate issues/diagnostics from actual installed 0.4 Test hardware, ensure no significant crash/regression signal, physically confirm relevant existing runtime regressions (#1503/#1501), and individually accept each new fingerprint intended for Live (or explicitly defer/remove those without adequate evidence). Never substitute a successful Homey manifest/CI test for real feedback.
