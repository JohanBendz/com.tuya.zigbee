# 0.4.0 Test readiness · 2026-10-02

**Target:** submit 0.4.0 to the Homey Test channel **6–7 October 2026**, subject to the *pre-Test static/release gates* below. **The Homey Test channel is our real-world physical testing and community feedback phase: completed physical acceptance of new devices is NOT a prerequisite to publishing Test.** This is a planning target, not a scheduled auto-release. Live/Test versions and Draft PR #1470 are not modified by this document.

## Evidence and scope

- Maintainer-reported 0.3.1 Test adoption on October 2: **over 2,600 installs and no crash or error reports received**. This is a report-status snapshot, not proof that crashes can never occur or that new 0.4 runtime is verified. The 0.3.1 Test line is at commit 7583b4bb2fa91600c2301eb142335312a6a7cac4.
- Preflight compared both generated Homey manifests property for property: 0.3.1 contains **135 drivers**; 0.4 adds **seventeen isolated new profiles**, and all **135 existing driver manifest objects are identical**. No existing Flow-card object or custom capability definition differs. This comparison was turned into a permanent automated baseline test: test/0.4-legacy-manifest-contract.test.js and immutable test/fixtures/0.3.1-manifest-contract.json.
- Seventeen new Compose drivers match 31 distinct Zigbee manufacturerName + modelId pairs pending independent physical acceptance, recorded in docs/0.4.0_PHYSICAL_ACCEPTANCE.md. No existing driver capability migrations or new Flow contracts have been introduced.
- Existing runtime changes requiring extra attention despite identical manifests: four opted-in plug runtimes (smartplug, smartplug_2_socket parent EP1, wall_socket, smartPlug_DinRail) using Tuya relayStatus 0x8002 (#1503); PLUS wall_thermostat's diagnostic-only limiter for high-frequency unmapped DP36 messages (#1501). The thermostat's recognized datapoint values/command handling is not intentionally changed.
- Existing intentional color-temperature audit TODOs (#1502) remain TODOs. The 0.3.1 byte-identical source baseline now includes five core shared Zigbee/Tuya runtime files AND all 15 existing light device.js files; CI checks actual Git blob identities using test/0.4-protected-runtime-contract.test.js. The shared light/runtime stack is too sensitive for a broad, unverified rewrite during this Test preparation window.

## Test-candidate gates

**Gate 1 – build/compatibility:** clean Homey Compose generation; generated app.json and SUPPORTED_DEVICES.md committed and reproducible; full Node test suite including the immutable 0.3.1 contract; Homey app validate at publish level; whitespace; review actual diff from frozen 0.3.1. Any intentional change to an existing driver, custom capability or Flow card must have an explicitly reviewed, issue-linked pinned entry in test/fixtures/0.4-approved-manifest-deltas.json. The 20 protected source files likewise must remain identical to frozen 0.3.1 or require an approved issue-linked exact blob in test/fixtures/0.4-approved-runtime-deltas.json. NEVER modify the 0.3.1 snapshot to make a new change pass. This catches a changed existing driver declaration even if the new code appears harmless.

**Gate 2 – release-channel decision:** review 0.3.1 Test feedback and explicitly decide whether 0.3.1 is promoted to Live before replacing the occupied Test channel, or retained while 0.4 becomes next Test. Do not silently merge Draft PR #1470, publish an app, or assume Athom's review timing. Homey Test users may receive newer Test updates: treat moving from 0.3.1 to 0.4 as a meaningful rollout, not a private smoke-test.

**Gate 3 – prepare the physical Test programme, not perform it before publishing:** make the public GitHub issue/reporting path, exact-identity acceptance matrix, rollback procedure and reporter instructions ready. No physical pairing, relay/sensor checks or completed hardware acceptance is required to submit 0.4.0 to Test. Once 0.4.0 is available in Test, collect real Homey feedback, prioritizing multichannel EP2/EP3 operation and physical status/Flow (#795/#1500), existing plug power-on-setting regression (#1503), wall-thermostat known datapoints and DP36 log behavior (#1501), and the four added temperature/humidity sensors, MOWE standard-IAS rain sensor (#1288), and three pending standard-IAS flood-sensor fingerprints (#1041; provisional unknown battery cells), and two exact contact + lux profiles (#1298; distinct EF00 endpoint requirements and unknown battery cells), and three plain standard-IAS contact profiles (#1013; Poll Control optional and two unknown battery cell specifications). Each manufacturer's actual result is recorded separately; missing or failed Test feedback remains an OPEN issue and feeds subsequent Test patches. Passing a mocked test is never described as physical acceptance.

**Gate 4 – Test release artifacts:** scope-checked changelog written for users that presents new variants as available for **testing**, not physically verified; supported-device index exact, pairing instructions and artwork validated, publish validation green at FINAL SHA, current rollback/version path documented. Check source file diff to ensure shared light and global Zigbee cluster handling were not modified inadvertently.

**Separate Live gate (AFTER Test):** evaluate issues/diagnostics from actual installed 0.4 Test hardware, ensure no significant crash/regression signal, physically confirm relevant existing runtime regressions (#1503/#1501), and individually accept each new fingerprint intended for Live (or explicitly defer/remove those without adequate evidence). Never substitute a successful Homey manifest/CI test for real feedback.

## Working sequence

- **Oct 2–3:** Freeze a trusted 0.3.1 compatibility contract in CI; inspect only narrow 0.4 regressions and evidence-backed device work. Do not trade regressions for issue-count reduction.
- **Oct 4:** Resolve outstanding code-review, targeted mocked tests and static regression checks; prepare clear GitHub reporting instructions and physical Test checklist. Do **not** block Test submission on hardware that can only be validated once Test is published.
- **Oct 5:** Candidate audit, Homey publish validation, final README/changelog/index and Test release-lane decision. Fix known static/publish blockers and unacceptable identified risk; ordinary *absence of physical testing* is expected at this stage, not a Test blocker.
- **Oct 6–7:** Submit 0.4.0 to Test once the **non-physical pre-Test Gates 1–4** are satisfied. Begin physical testing **through Test installs**: community pairing, EP-by-EP switching/Flow, plug and thermostat regression, and sensor behavior. Triage reported failures into narrow 0.4.x Test corrections. Do not describe all 20 new identities as already verified.
- **Following Test feedback:** perform the distinct Live acceptance review using real installation reports; hardware verification is a Live/support-claim decision, NOT a requirement to open Test.

Useful official references: https://apps.developer.homey.app/app-store/publishing and https://apps.developer.homey.app/app-store/updates. Homey apps use semver; a lower-version release cannot force a downgrade.
