## Pre-Test decision register

- **Static contracts / old-user compatibility:** prior CI GREEN at audit start.
  Recheck final tree and all changes after this snapshot. Do not rewrite the immutable
  0.3.1 fixtures or weaken the protected-runtime test to obtain a pass.
- **Scope and device identities:** 33 exact profiles-inventory rows, verified
  mechanically in `test/0.4-physical-acceptance-inventory.test.js`.
  This includes all new driver manufacturer/product combinations, with no
  unsafe eWeLink/SNZB-03 matcher: a PIR (#1113) and SQ510A water sensor (#1475)
  share that exact identity and are deliberately deferred.
- **Test reporting path:** [exact physical acceptance and copyable test report](0.4.0_PHYSICAL_ACCEPTANCE.md).
  Record actual app version, exact Zigbee identity, driver, Homey firmware, device
  behaviors, Flow, restart/rejoin and real cell type/count. Do not put private IEEE
  addresses, network IDs or access tokens in public issues.
- **Manual UI / artwork / pairing check:** review new profile names, icons, images and
  instructions in Homey pairing preview, especially inherited artwork shared by
  isolated driver profiles. The successful automated validator is necessary but is
  not a substitute for the maintainer's visual review.
- **0.3.1 feedback and Test-channel transition:** **CONFIRMED: 0.3.2 Live BEFORE 0.4.0 Test**.
  The maintainer originally selected 0.3.1 Live first in tracker #1469 / PR #1470,
  then selected a documentation-only 0.3.2 resubmission on 2026-10-04.
  `release-0.3.2` preserves the frozen 0.3.1 runtime; only publication copy,
  version metadata and packaging/maintenance files change. See [the correction](0.3.2_PUBLICATION.md).
  Review feedback and existing-device upgrade/Flow behavior, validate the final
  0.3.2 SHA, complete Athom certification, and confirm actual 0.3.2 Live
  availability BEFORE submitting 0.4.0 to Test. The [0.3.1 review checkpoint](0.3.1_LIVE_REVIEW.md)
  remains evidence for the inherited runtime, not a claim that 0.3.2 is published.
  Publication is still pending; no release-PR merge is implied by this checklist.
- **Physical verification of new profiles:** deliberately **PENDING until public
  0.4 Test**; it is not an entry gate for publishing Test. It DOES matter before
  claiming device support is fully verified or proposing a later Live rollout.

## Priority order when 0.4.0 becomes publicly available in Test

1. Smoke-check upgrade, pairing and existing critical light/Flow behaviors with
   current users; monitor crashes, initialization errors and rollback readiness.
2. Regress four pre-existing plug drivers' relay_status behavior (#1503): optional
   0x8002 read, supported value 0/1/2, no silent default write, unaffected onoff.
   Check wall_thermostat recognized DPs versus diagnostics-only DP36 suppression (#1501).
3. For multi-channel switches, test each independent EP/tile both from Homey and
   physical switch, including Flow/report feedback; prioritize #1500, #795,
   #1338, #991 and #1035.
4. Physically test all 33 new identities separately using the [acceptance matrix](0.4.0_PHYSICAL_ACCEPTANCE.md).
   Standard ZCL contact/rain/motion/water/battery/lux and the four temperature/RH
   sensors require real report values, polarity and accuracy. Check actual battery
   type/count where marked `OTHER`; validate illuminance conversion against real
   light levels and motion/cooldown/clear, not just whether a device paired.
5. Keep canonical issues open for individual missing or failed results. A positive
   report for one manufacturer must never be generalized to another exact ID.

## Recovery / rollback policy (version-safe)

- **Before 0.4 Test submission:** retain the frozen 0.3.1 branch, its validated SHA
  unchanged. Keep PR #1470 as the frozen 0.3.1 reference and use the separate `release-0.3.2` submission lane. Stop or defer the submission if a reproducible
  static blocker is found. There is no need to roll back a version that is not
  yet published.
- **After 0.4.0 is published to Test:** do **not** assume that publishing 0.3.1
  again will downgrade installed 0.4.0 Test apps; Homey release versions are
  monotonic. If a critical fault appears, pause further promotion, document
  the affected fingerprints and produce a **higher-version corrective Test build**,
  normally 0.4.1. Depending on scope, selectively revert the offending 0.4
  changes or build a conservative 0.3.1-compatible source tree released under
  the higher version. Update ALL relevant version metadata, Homey Compose,
  generated app.json/index, changelog and tests; run full CI and publish
  validation on the exact corrective commit.
- Keep 0.2.76 Live and the untouched 0.3.1 source available as references.
  Do not automatically merge #1470 or bypass Athom review. A subsequent Live
  promotion has its own acceptance decision and must evaluate individual
  public Test evidence, not simply the green mock-test result.

## Feature freeze and next development lane

The 0.4.0 feature scope is frozen at the implementation inventory above: 154
drivers, 19 new profiles and 33 exact acceptance rows. `develop-0.4` is the
0.4.0 stabilization/release lane; only identified release blockers, reviewed
0.3.0/0.3.1 feedback fixes and release documentation belong here, followed by
CI on the selected final SHA. Freeze is not an assertion of final sign-off.

Create `develop-0.4.1` from the validated freeze checkpoint for all new
development. It initially inherits unchanged 0.4.0 version metadata; advance
package/lock/Compose/generated manifest/changelog together when preparing the
first 0.4.1 implementation candidate, and adapt candidate-specific preflight
checks explicitly. Do not silently add new work to the frozen 0.4.0 scope or
merge the 0.4.1 branch wholesale back into it. Narrow fixes discovered during
Test may be selectively carried between lanes with independent validation.
