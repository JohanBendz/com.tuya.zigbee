# 0.4.0 physical acceptance and release gates

Recorded 2026-10-02. This is the inventory of **21 distinct exact Zigbee identities in nine NEW development drivers** relative to frozen 0.3.1 Test. **This is the community's physical TEST plan, to be executed after 0.4.0 is published to Homey Test; no row must pass physically before Test publication.** A Homey Zigbee interview establishes actual identity and announced endpoints, NOT working functionality in the newly added 0.4 driver. A passed build, unit test, Compose/index check or publish validation is not physical acceptance. Independent testing in a third-party fork or private Homey driver also is not acceptance of these 0.4 changes.

## Release-lane boundary

- Current legacy Live: **0.2.76** (SDK3). Frozen current Test: **0.3.1** (modernize-2026-issues at 7583b4b). Draft PR [#1470](https://github.com/JohanBendz/com.tuya.zigbee/pull/1470) needs explicit maintainer review of actual 0.3.1 Test feedback.
- At inventory start, 0.4 development HEAD was 3a065cd87c2f7ff64b3272ac68c89b300eec66d6; [CI 36976674058](https://github.com/JohanBendz/com.tuya.zigbee/actions/runs/36976674058) passed **145 tests, 142 pass, zero failures, three pre-existing CCT TODOs**, with Homey publish validation.
- **0.4 is not yet published to Test or Live** as of this document: the published 0.3.1 cannot validate these new drivers. The intended normal route is to **publish 0.4 to Test and gather physical feedback there**. An optional developer build is helpful but never a mandatory pre-Test hardware gate. The Test-channel transition still needs an explicit maintainer release-lane decision.

**Gate A: before publishing 0.4 Test (NO physical-test prerequisite).** Examine reported 0.3.1 feedback; make a separate release decision for #1470 and the occupied Test channel; prepare issue reporting and an explicit rollback version. CI at the exact 0.4 candidate SHA must be green (Compose build, generated app.json, SUPPORTED_DEVICES.md, tests, Homey publish validation, whitespace); review manifest compatibility and sensitive legacy light/global cluster protection, and rule out known reproducible release-blocking source-level issues. **Publish to Test with new fingerprints explicitly marked unverified so that actual users can test them. No Test pairing results or completed hardware checklists are demanded in advance.**

**Gate B: during 0.4 Test and before a subsequent Live release.** Collect and triage the exact hardware tests below **from users running the published 0.4 Test version**; attach evidence to each original/canonical GitHub issue and close only separately verified scope. Missing reports are normal when Test first opens. Before claiming full physical support or publishing Live, evaluate reports and regressions; if an included identity has inadequate evidence, explicitly assess/defer/remove it rather than treating another manufacturer's result as acceptance. Test changed existing plug drivers (#1503) and wall-thermostat logger (#1501) during the Test rollout. Research-only light gate #1502 and three intentional CCT TODOs remain separate.

## Switch acceptance protocol (for Homey 0.4 Test users; perform per exact row)

Use an approved non-production test Homey when possible; do not remove a reliable production pairing merely to provide a test. Any necessary mains electrical work must be done safely by a qualified person.

1. Record real Homey hardware/firmware, exact 0.4 build SHA, retail model, manufacturerName, modelId and selected driver. Count created tiles. Do not mistake Green Power endpoint 242 for a relay.
2. Independently issue Homey OFF → ON → OFF on EACH tile; check correct physical output with no unintended other-gang action. Then operate EACH physical switch/button and ensure Homey receives both OnOff transitions with correct state.
3. Verify correct Homey Flow triggers on EACH tile/channel. Expected mapping: parent EP1, secondSwitch EP2, thirdSwitch EP3, fourthSwitch EP4. Capture delayed, inverted or missing reports and failed sequence.
4. Check app restart, Homey restart, rejoin and safely arranged mains loss/restore where relevant. Observe power-on state but DO NOT assume a configurable manufacturer setting exists. Previously paired Generic Zigbee/other-app devices are not automatically migrated to new driver IDs.

## Existing plug Power-On State regression DURING Test #1503

These do not add identities in the matrix but WERE changed in 0.4: smartplug, smartplug_2_socket (parent EP1 only), wall_socket and smartPlug_DinRail.

- On actual supported firmware, startup must only READ Tuya relayStatus attribute **0x8002**, normalize 0 Off / 1 On / 2 Remember into existing Homey relay_status, and send ZERO power-state writes until a user deliberately changes the setting.
- A missing/unsupported/unknown relayStatus must preserve the Homey setting and not interrupt normal switching; unsupported childLock or indicatorMode reads must not suppress a supported relayStatus read.
- Verify deliberate user writes of 0/1/2, optional readback and safely observed mains restoration on a non-critical load. Failed Zigbee writes must surface as failures to Homey. Do not confuse Tuya 0x8002 (previous = 2) with standard Zigbee StartUpOnOff 0x4003 (previous = 0xFF), and do not blindly add this option to newly paired generic TS000x switches.

## Existing wall-thermostat diagnostic-only regression DURING Test #1501

The existing `wall_thermostat` runtime also changed in 0.4 despite the byte-identical 0.3.1 driver manifest: it now throttles **identical unknown datapoint log messages** (e.g. physically observed DP36) for 60 seconds and summarizes suppressed repeats. This is a logging change, NOT new DP36 interpretation or reduced Zigbee traffic. If a representative device is available, confirm normal known DP1/DP2/DP16/DP24/DP40 Homey values/Flow remain correct, the first new unknown DP/value is still logged immediately, a changed unknown value remains visible, and a repeated value does not flood logs. Record the exact hardware fingerprint before proposing any new DP mapping. See [#1501](https://github.com/JohanBendz/com.tuya.zigbee/issues/1501).
