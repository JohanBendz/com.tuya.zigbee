## First implementation batch: #1026

Only `drivers/smart_remote_1_button_2/device.js` changes device behavior.
It retains the exact `_TZ3000_ja5osu5g / TS004F` matcher, Homey driver ID,
capability list, settings and `smart_remote_1_button_2` Flow actions.

- Accept only endpoint-1 cluster-6 cluster-specific Tuya action command 0xFD,
  with a valid three-byte non-manufacturer ZCL header and one action byte.
- Map 0/1/2 to the existing oneClick/twoClicks/longPress values. Reject unknown
  actions and malformed/truncated/unverified frame forms as gestures.
- Support native Buffer and serialized Buffer input without mutating it.
- Preserve the captured ZCL dispatcher, receiver, metadata, return value and
  error behavior for all other traffic, including the standard OnOff command
  that follows each captured gesture. Consume a recognized gesture only once.
- Reinitialization must not stack wrappers; device deletion restores the
  original dispatcher only while this device's wrapper is still installed,
  and still invokes the SDK's listener/interval cleanup.
- No timer debounce, alternate-frame counter, new capability, battery
  implementation, manufacturer additions or shared-cluster changes.

The original #1026 captures are the concrete regression input. The new
`test/single-button-1026.test.js` exercises the actual driver with Homey/Zigbee
stubs: captured single/double/hold pairs for both Buffer representations,
invalid/unknown packets, ordinary ZCL traffic, rapid legitimate presses,
sequence wrap, hook lifecycle and failure propagation. The old source failed
eight of the nine tests; all nine pass after correction. This is automated
evidence only.

## Physical acceptance through public Test

Keep #1026 OPEN. Once this version is actually available through Test, record
exact app version/commit, Homey model/firmware and manufacturer/model. Existing
pairings should not need replacement because no pairing/Flow contract changed.

- One single click produces exactly one oneClick and no false hold/double.
- One double click produces exactly one twoClicks.
- A physical hold produces one longPress as actually emitted by the unit.
- Standard follow-up frames do not trigger a second Flow.
- Repeated legitimate clicks still work without a new time lockout.
- Existing saved Flows still filter by the same action strings.
- Restart/rejoin and unrelated standard report handling remain normal.

The request's optional battery display remains unimplemented and must not be
described as delivered. Hardware feedback happens in Test, not as a prerequisite
to opening Test. Any newly demonstrated published-version regression receives
a separate patch decision; this batch does not publish or update main/dev.
